# Standalone POS staff authority review

Review date: 17 November 2026. This note traces the native checkout and the existing counter/owner authentication primitives. It is an integration design, not evidence that the standalone checkout has staff authorization today.

## Findings

The current standalone checkout is explicitly a test host (`CheckoutActivity`). It starts a Regtest watch-only counter, stores the pairing bundle in `SealedFile` using `KeystoreSealer`, initializes a separate `CheckoutLedger`, and immediately opens checkout or sales. There is no sign-in gate, authenticated staff session, role check, or owner-authenticated approval in this activity. The Keystore wrapper is AES-GCM device-key encryption for a blob; it does not prove which staff member is using the app, ask for a PIN, or gate an operation. The native checkout ledger currently does not persist an actor on sale, cash, card, or refund-request entries. `requestRefund` is reachable from the receipt UI and records a bounded request after a confirmation dialog; that dialog explicitly says it does not issue a provider refund or move funds.

Existing counter app primitives are materially stronger than a role/name field, but are scoped to that app:

- `PinStore` and `StaffStore` persist salted PBKDF2-HMAC-SHA256 verifiers (600,000 default iterations), count and durably save each try before comparison, apply escalating holds, and fail when the durable write fails. The manager PIN is 6–12 digits; cashier PINs are 4–8 digits. Staff records live in `noBackupFilesDir`; the PIN files are not encrypted by Android Keystore and are not transferred to another phone. A corrupt file fails closed.
- `TillLock` keeps the signed-in `Actor` in memory only, starts locked after process stop, locks after more than five minutes out of view, and defers a due lock while a sale screen is open. Sign-in results that return after the app is hidden are discarded.
- The counter controller checks the PIN before calling protected workflows. Its `ActorRole`/`Actor` is a caller-supplied result of that check, not an authenticated identity on its own. Counter library methods generally enforce business limits and role ceilings, not the truth of the caller's PIN check. The `refund.rs` comments explicitly say “The caller has already checked the PIN.”
- `staff.rs` writes an owner-visible audit record of cashier add/remove and manager name. It never stores PINs or PIN-derived material. This is an audit event, not a `staff_permissions` capability grant. I found no `staff_permissions` symbol or capability-record subsystem in this checkout source tree.
- Existing owner authentication in the owner app protects owner key material with a local PIN/passphrase lock (`openbmt-lock`/`OwnerLock`); it is separate from counter staff identity. Owner app setup includes the owner's signing secret, and the owner node holds signing authority. Do not reuse the owner PIN as cashier authentication or expose owner signing calls through POS authorization.

The separate sale contract already states the right target separation: cashier may create sale/initiate allowed tender; read/report may read; refund request cannot approve or execute owner-restricted action; inventory cannot sign; owner settings control wallet/destination/signing; spending remains with existing wallet authority. It also correctly calls out role-based staff permissions as absent in the native ledger.

## Permission matrix for the standalone POS

Identity source means a successful PIN verification against the local staff verifier store followed by issuance of a short-lived, in-memory session bound to the selected staff record. The actor name/role in a ledger event is audit context only. The authorization boundary must receive an opaque authenticated session/principal and re-check capability at the command boundary; passing `ActorRole` or a string alone is not authorization.

| Action | Cashier | Manager | Owner | Identity and enforcement |
|---|---|---|---|---|
| Create sale, edit pre-tender cart, initiate permitted tender, record cash tender | Allow | Allow | Allow | Active staff session; command gateway checks session freshness and role. Persist actor ID/session evidence with mutation. |
| Read receipt and own/store sales, tender status, ordinary reports | Allow | Allow | Allow | Authenticated session; report scope follows configured policy. For MVP, read-only access may be available after sign-in only. |
| Request card/Bitcoin refund against settled original tender | Allow only to submit bounded request | Allow | Allow | Requester session required; persist request and requester principal. It creates an obligation only, never invokes provider refund/wallet spend. |
| Approve/execute a refund or resolve payment ambiguity for fulfillment | Deny | Deny by default; no capability in initial standalone role set | Owner-only explicit approval path | Fresh owner authentication, separate approval event, original sale/tender binding and audit event. Execution is only through the already-authorized provider/wallet API, never a generic payout. |
| Append independently verified card/Bitcoin payment or refund evidence to an existing attempt | Deny as a manual staff command | Deny as a manual staff command | Deny as a manual staff command | A private trusted provider callback adapter or an already-authenticated native node observation may append evidence while the staff session is locked or expired. Record actor as `SYSTEM` plus source identity and existing attempt ID. A staff label, role, or manually supplied `SYSTEM` string cannot mint observer authority. |
| Add/remove staff, reset staff PIN, change permission policy, change shop-wide pricing/tax/inventory policy | Deny | Allow | Allow | Fresh manager session (or owner); durable audit event identifies authenticated principal. Staff changes revoke affected sessions immediately. |
| Change owner keys, wallet/destination, signing settings, recovery credentials | Deny | Deny | Owner only | Existing Owner app authorization and existing key ceremony. POS cannot delegate or mint these capabilities. |
| Sign Bitcoin spend / arbitrary transfer | Deny | Deny | Existing wallet authority only | No POS staff capability. Keep signer/key paths unreachable from cashier, manager, and standalone session code. |
| Unknown or malformed role/capability, corrupt auth store, failed verifier write, expired/revoked session | Deny | Deny | Deny until owner recovery succeeds | Fail closed; do not fall back to implicit manager, first-run cashier, role string, or prior in-memory state. |

## Integration design using current primitives

1. Reuse the counter PIN verifier and throttling logic (`PinCheck`, `PinStore`, `StaffStore`) as the password-verification mechanism, but put the new standalone POS staff store behind `DurableFile` in app-private no-backup storage and protect the store at rest with a dedicated Keystore key/AAD envelope if the platform wrapper can support it. Keep verifier salt/hash private; never put PIN material in sale records, logs, exports, audit records, or provider metadata. A Keystore key is encryption-at-rest support, not user authentication.
2. Add a native `StaffAuthority` command boundary. `signIn(staffId, pin)` resolves staff from a strict store, verifies and persists failure/hold state before comparison, then returns an opaque process-local session with immutable staff ID, assigned capabilities, issued time, and generation. Mutations accept that session/principal, not an arbitrary `Actor`; the gateway checks the current staff record, allowed capability, session generation, expiry/lock state, app visibility, and revocation before invoking pure module models or side effects. Do not trust a UI-hidden button as the control.
3. Fail closed for absent/corrupt auth data, unknown schema versions, unknown roles/capabilities, duplicate staff IDs, verifier-write errors, expired sessions, stale generations, or a command started before the app was backgrounded. First-run bootstrap may create only the owner/manager credential through an explicit local enrollment path; it must not silently create an authenticated owner session or grant owner signing power.
4. Keep staff identity distinct from shop owner identity. A manager may administer staff and can submit bounded refund requests; owner approval is a different event requiring existing owner authentication. Request, approval, external execution, and observed paid evidence need distinct IDs/events and actors. A request cannot mutate to paid merely because a provider call was attempted or returned pending. Refund handling remains constrained to original settled tender; no transfer destination, generic withdrawal, or new wallet-spend operation is added.
5. Use persistent stable staff IDs, not display names, as principals. Names and role strings can be displayed and included as denormalized audit context, but they are mutable and spoofable. Persist the capability decision/version with privileged events so later policy changes do not rewrite historical authority. Unknown capabilities must be rejected rather than ignored.
6. Revoke all staff sessions on app process restart, manual lock, app background/visibility timeout, staff removal or PIN reset, role/capability change, owner recovery, and auth-store repair. Match `TillLock`'s in-memory-session baseline (locked on process restart and >5 minutes away), but do not defer expiration while a cart, receipt, refund dialog, or payment UI is open. Require a fresh session immediately before starting a new privileged command or new external collection/refund side effect. Do not apply that staff-session check to evidence returned by an operation that was already durably started: a private trusted provider callback or authenticated native node observer must append and reconcile the response against the same attempt/refund identity even after logout, timeout, or app restart. These evidence events are tagged `SYSTEM` and the trusted source identity, never attributed to the expired cashier or to a caller-supplied role. If evidence is pending or ambiguous, preserve it and reconcile the same stable identity; do not launch a replacement collection or spend.

## Owner recovery and offline/revocation boundary

Owner recovery should use the existing owner phone's locked key setup and documented owner recovery ceremony. A POS manager PIN reset is not owner recovery. If the last manager credential is lost, staff administration remains locked until the owner authenticates through the existing Owner app and performs an explicit local recovery/reset ceremony. Recovery must preserve the local sale/tender/refund ledger and write an audit record identifying owner recovery; it must not clear unknown payment outcomes, refund obligations, or change wallet authority. If the owner device/key is unavailable, staff may continue only the capabilities already granted to valid current sessions; no default or emergency manager bypass exists.

All authentication and authorization can run offline because the verifier and policy snapshot are local. Offline mode does not establish remote revocation. A removed staff member's device may remain usable until the next local synchronization if staff credentials were copied across devices; therefore the initial standalone design should be single-device/local-store only. Do not imply cross-device revocation or centralized capability issuance. If a future multi-device mode is added, it needs authenticated owner-signed policy/revocation records, monotonic policy versions, and fail-closed stale-policy behavior; that is not part of this integration.

## Acceptance gates

- Fresh install is locked at staff enrollment/sign-in; no checkout, sale mutation, refund request, or module command is callable without a valid authenticated session.
- Wrong, held, unknown-ID, malformed-role, corrupt-store, and failed-write cases never yield a session. Failed-attempt count/hold survives process death. The PIN check is durably recorded before hash comparison.
- Manager/cashier capability matrix is enforced at the native command boundary, including direct calls that bypass UI. Unknown roles and capability IDs reject.
- Restart, lock, timeout, app background, staff removal, PIN reset, and policy generation changes invalidate existing sessions; stale user callbacks cannot launch a new external operation or commit a new user command. Independently authenticated evidence callbacks remain able to append to their pre-existing stable attempt while locked.
- Expired/revoked staff cannot initiate a new collection, refund execution, fulfillment, or configuration change. A verified response to a previously persisted attempt can still be appended by the private provider/native-node observer and reconciled while locked, with `SYSTEM` plus source identity and the original stable attempt ID.
- A cashier or manager cannot create a `SYSTEM` event by entering that string, selecting an enum value, passing a role name, or submitting manual payment/refund evidence. The evidence adapter accepts only its private provider callback/native node handle and validates the observation against the already existing attempt.
- Late card completion and late Bitcoin receipt while locked update the same durable attempt/refund state without a new charge, a fulfillment shortcut, or a wallet spend. Restart preserves this reconciliation path.
- Audit records carry stable principal ID, event type, policy version, and event/request ID, but contain no PIN/verifier material. Display-name edits do not alter principal identity.
- Cashier refund request is bounded by independently evidenced settled value and original tender; it records requester only. It cannot approve, execute, claim paid, create a payout destination, or authorize wallet spend.
- Owner approval is separately authenticated, explicitly bound to a specific request and amount, and cannot exceed settled balance. Pending/unknown provider outcomes remain pending/reconcilable, and retries reuse the same idempotency key.
- Owner recovery restores staff administration while preserving all sale, tender, request, evidence, and unresolved states. Recovery cannot manufacture a refund execution or wallet authorization.
- Offline operation grants only the locally stored policy. The product makes no claim of remote revocation until a trusted fresh policy/revocation record is received.

Current source supports several verifier and lifecycle building blocks in the counter app, but the native checkout has none of this end-to-end authority integration. Treat all gates above as unmet until wired through the standalone cashier/manager/owner command path and observed in the acceptance harness.
