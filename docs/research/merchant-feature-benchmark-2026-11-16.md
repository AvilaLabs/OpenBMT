# Bitcoin merchant payment feature benchmark

Research snapshot: 16 November 2026; implementation status addendum dated 16 November 2026. This is a recommended OpenBMT backlog, not an adoption of another provider's custody or settlement model. The [merchant product plan](merchant-product-plan-2026-11-16.md) records the accepted wallet authority choices and implementation order. The [standalone POS delivery plan](standalone-pos-delivery-plan-2026-11-16.md) sets the current product sequence.

The companion [practical friction review](btcpay-practical-friction-2026-11-16.md) examines firsthand complaints, current scope decisions, and historical fixes, and turns them into merchant validation criteria.

The largest product gap is a dependable interface between payment evidence and merchant operations: invoices, status queries, signed events, refunds, fulfillment, and records that reconcile after interruption. Local durable events belong in that foundation; webhooks are an optional outward-facing adapter. Native checkout, receiving automation, and cold-wallet support remain necessary; copying a processor's feature list alone does not establish merchant convenience.

## Scope and evidence

The comparison covers BTCPay Server, Bitcart, LNbits and its merchant extensions, SatSale, ZEUS, Alby Hub, Phoenixd, selected Breez SDK documentation, OpenNode, CoinGate, and Strike. Features below are documented capabilities, not results from accounts or live merchant deployments. App, plugin, node, SDK, and hosted-processor capabilities are kept distinct. Version and backend compatibility must be checked when an integration is built.

## Implementation status addendum

The following current implementation details were added after the benchmark source snapshot. Scoped checks passed: 1,181 Rust tests, strict Clippy, the complete checkout JVM harness, both Android ABI builds, the Square Sandbox module build, APK signatures/alignment, and Android emulator cash/restart/history checks. See [validation evidence](../../tools/merchant-acceptance-investigation/evidence/standalone-foundations-2026-11-16.json). These checks do not establish a complete POS or production readiness.

The following narrow implementation slices are available:

- Native checkout ledger v6 includes a USD cash-tender journal, `initializeEvents`, an event snapshot/replay path bounded to 1,000 events, and atomic state updates. It does not implement the owner Requests API or a general commerce API.
- Native history supports ID/item search and tender/status filters; its API supports date-range filtering.
- Receipt copy/test uses a privacy-limited projection only; no physical printer or email delivery is implemented.
- `openbmt-core::capabilities` models verified metadata for authorization, revocation, expiry, and exact store/register scope; authenticated transport and staff screens are absent.
- Books reconciliation CSV includes exact satoshi amounts and timestamps. Export requires the payment-disclosure warning acknowledgment; the narrower accountant export is unchanged.
- `Node::receiving_assessment` provides point-in-time confirmed-funding and strict/lazy-queue status, not a route guarantee.
- A two-item sample cart exists; it is not a configurable catalog or tax/modifier engine.
- The SP-88 UTXO maintenance advisory reports cost thresholds; it does not automate coin selection, consolidation, or signing.

These narrow slices do not close the remaining backlog below. Their test evidence is limited to the cases above; the remaining backlog is unchanged.

## Serverless events and optional webhook delivery

BTCPay's integration guidance covers payload authentication, idempotent processing, status reconciliation, and manual event redelivery. CoinGate separately documents bounded callback retries. These are useful reliability patterns; OpenBMT should implement its own precise event contract instead of inheriting either processor's account model or retry timings. [BTCPay integration](https://docs.btcpayserver.org/Development/ecommerce-integration-guide/), [CoinGate callbacks](https://developer.coingate.com/reference/api-callbacks)

OpenBMT should not require the merchant to install a BTCPay-style web server. A local event interface serves the native checkout. An optional outbound webhook bridge can send events to the merchant's existing store or automation endpoint; the app needs no public listener. Public REST hosting is an optional deployment with its own authority/privacy review.

The proposed event contract and optional bridge should include:

1. A durable local event log committed with the corresponding payment/sale state. When enabled, the outbound bridge tracks delivery in an outbox rather than relying on an in-memory HTTP call.
2. A stable event identity, resource identity and version, timestamp, schema version, and a separate identity for each delivery attempt. Retries retain the same event identity. Do not promise exactly-once or arrival order.
3. Separate observed-payment, policy-confirmed payment, partial/late/excess payment, invoice expiry, reorganization, refund, and fulfillment states. Exact names are to be specified; a low-confirmation receipt is not silently relabeled final.
4. Per-endpoint authentication with signatures over the exact body, credential rotation/revocation, and explicit receiver verification before acting.
5. Bounded retry/backoff, visible delivery results, a failed-delivery queue, test delivery, and manual replay that does not create a second business action.
6. A query/event-cursor interface for repairing gaps and comparing current resource state after restart. Remote stores cannot assume a sleeping or unreachable app exposes this interface; define outbound synchronization or a reachable merchant-operated arrangement separately.
7. Default payload minimization: opaque references and necessary state, without secrets, wallet descriptions, customer identity, addresses, or transaction IDs. Merchant-selected additional metadata and endpoint ownership require explicit disclosure.
8. No default OpenBMT company relay, account, or telemetry. Support local/pull interfaces and merchant-operated delivery; assess each third-party destination under the privacy policy.
9. Defined availability: an asleep/offline app cannot guarantee immediate observation or delivery. It reconciles and replays later. Continuous ecommerce automation needs a separately evaluated availability arrangement; that is not a default server requirement for native checkout.
10. Boundary tests for duplicate, delayed, missing, out-of-order, unauthorized, and replayed events; receiver crashes; revoked credentials; and state changes during reconciliation. A webhook must not grant wallet spending authority.

The current [network contact rules](../handbook/network-reference.md#never-telemetry-analytics-or-crash-upload) do not already authorize generic outbound callbacks. Add the recipient, data, permissions, and failure behavior to the plan/contact inventory before implementing the new interface. Owner-selected notifications are not permission for silent publisher collection.

A checkout/API that distributes payment destinations needs its own destination-authority review. Minimal webhook metadata does not authorize passing wallet descriptions or payment addresses through the current Box, whose role explicitly excludes that data.

## Features and product models to exclude

| Model | OpenBMT decision |
| --- | --- |
| A processor holds Bitcoin, can freeze its release, or is required to approve recovery | Exclude from the baseline. An attractive checkout does not justify delegated custody. |
| Mandatory fiat conversion, stablecoin settlement, altcoins, or issuer balances presented as merchant Bitcoin | Exclude. Fiat price display and reporting are separate from settlement. |
| Provider-held fee credit or customer wallet balances | Do not adopt as a generic Bitcoin wallet. Distinguish purchase proceeds, merchant liabilities, and actual key control. |
| A required publisher account, global payment server, or company sales-history upload | Exclude as a condition of receiving or recovering Bitcoin. Optional merchant-selected integrations remain scoped choices. |
| Universal merchant-initiated auto-debit of arbitrary Bitcoin wallets | Do not promise it. Explicit payer authorization is a different capability; prepaid credits need their own liability and purity assessment. |
| Automatic conversion through Liquid, Spark, ecash, or another settlement system merely to gain an SDK feature | No adoption follows from this benchmark. These are distinct systems requiring separate trust and recovery review, not interchangeable Bitcoin/Lightning backends. |
| A default API/NWC connection with spending or arbitrary-signing permissions | Exclude. Separate receive/read capabilities from financial authority. |
| Automatic extensions or updates that expand signing authority | Exclude silent installation/permission expansion. Preserve owner-chosen updates and reviewable interfaces. |
| Exactly-once callbacks, guaranteed mobile background receipt, guaranteed low fees, or software limits described as hard loss caps | Reject the claim unless the actual mechanism establishes it. Design retries, reconciliation, fee exceptions, and recovery explicitly. |

Self-hosting, open source, a watch-only screen, or a noncustodial label alone does not settle the funds-control question. LNbits account balances depend on the configured funding source. Alby account features, Lightning-address servers, hosted nodes, and liquidity services have different roles and permissions. SDK families using Greenlight, Liquid, or Spark must be assessed separately; no shared brand name makes their trust assumptions equivalent.

## Recommended next delivery slices

Standalone OpenBMT POS is the first product path; existing POS integration follows after its release gates. Several supporting primitives are now implemented with scoped checks passed (status addendum above), so the next finite work should complete end-to-end merchant behavior rather than restate them as proposals:

1. Validate the v6 local cash journal, event initialization/snapshot/replay, atomic state updates, native history, receipt projection, scoped capability metadata, Books CSV, receiving assessment, and SP-88 advisory. Keep each capability at its stated boundary.
2. Complete the canonical sale/tender contract around the current sample basket and cash journal. Add configurable catalog, modifiers, tax, discounts, tips, and immutable exact-money snapshots; reconcile Bitcoin, cash, and optional card using explicit partial, unknown, split, late, excess, canceled, refund, and fulfillment states.
3. Complete local recovery and owner exception handling, inventory-once behavior, tender-level receipts and refunds, role screens/permissions, cash opening float/in-out/count/close, supported peripheral tests, and USD day-close reporting.
4. Use the tested Square MPS Sandbox path as the card adapter starting point, while treating production eligibility, country/account/device support, physical readers, key isolation, and privacy review as unproven gates. Cash remains processor-free; Bitcoin remains independent of card authorization.
5. Validate a full merchant shift on intended physical devices and staff before POS adapters. Then select existing-POS integrations based on measured merchant need. Keep the local events API, owner Requests API, webhooks, printing/email, full accounting, additional card adapters, online/unattended workflows, and multi-location support as separate backlog items until implemented and validated.

Follow the [standalone POS delivery plan](standalone-pos-delivery-plan-2026-11-16.md) for exit evidence. A primitive or passing unit test does not by itself establish a merchant-ready workflow.

No competitor's marketing promise establishes OpenBMT readiness. Validate installation, ordinary-wallet payments, interruptions, key authority, and recovery in the deployment being claimed.
